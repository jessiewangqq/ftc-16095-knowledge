# 测到什么程度，可以合并代码

先说明这次功能要做到什么，再检查是否真的做到了。普通文字修改按实际影响检查，不要求每次跑整台车。改变机器人动作的代码需要对应的实车记录。

## 合并前逐项确认

- [ ] 有任务卡，写明要完成的动作、通过条件和谁来做。
- [ ] 代码可以构建；本次需要的电脑检查已运行，失败有处理结果。
- [ ] 测试前已经提交代码和参数，工作区没有未提交修改，构建安装的版本与记录 SHA 对应。
- [ ] 正常操作、边界、取消与恢复、DS STOP 都按本次影响范围测过。
- [ ] 原来可能被改坏的功能重新试过，例如改 RB 后检查取球、送球与射击。
- [ ] 每次结果可查看，写清车、参数、输入步骤和失败情况，关键问题已经处理。
- [ ] 操作说明已更新，另一位队员能照着完成需要的操作。
- [ ] 普通改动至少 1 位非作者批准；核心控制至少 2 位非作者批准，其中一位了解并核对实车动作。
- [ ] 主干新增改动、解决冲突或 review 后继续修改的部分，已重新检查并更新测试版本。
- [ ] PR 的问题和讨论已处理，知道出现问题怎样恢复。

核心控制包括驱动、取球、送球、射击、自动、停止、硬件参数和共享接口。RB 例子影响几个机构，按两位非作者检查。

## 合并后还要做什么

合并后的主干可能是一个新的 SHA。用最终版本重新构建、安装，检查启动、停止和受影响的动作，并写入[版本登记](../releases/REGISTRY.md)。如果改动影响更大，要重做相应的完整测试。

“能构建”“功能已合并”“整场可用”分别记录。准备上比赛的版本还要通过[整车检查](../releases/CHECKLIST.md)，不能只看 GitHub 上已经合并。

这份清单是本队协作约定，不是 FIRST 官方对 Git 的要求。平台是否强制执行 review，见[仓库设置](../GITHUB-SETUP.md)。
