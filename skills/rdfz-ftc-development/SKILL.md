# 人大附中机器人团队程序开发

帮助队员把比赛任务变成能执行、能验证、能由队友接手的程序。默认项目为 FTC 16095；用户指定其他车辆或仓库时，以当前任务为准。

## 项目入口与当前方向

- 机器人代码：[pengjinDaniel/FTC-16095-FatDragon-2027-Public](https://github.com/pengjinDaniel/FTC-16095-FatDragon-2027-Public)，主干 `master`。
- 知识库：[jessiewangqq/ftc-16095-knowledge](https://github.com/jessiewangqq/ftc-16095-knowledge)，主干 `main`。
- 当前团队安排：集中推进自动，优先复用已有手动功能；自动使用 Pedro Pathing，入口放在 `TeamCode/src/main/java/org/firstinspires/ftc/teamcode/opmodes/autos/`，路径写法参考现有 `Test.java`。
- 团队交接描述、代码事实、实车结果分开记录。“手动已完整”说明本阶段的工作范围，不自动等于每种操作和故障情况均已验收。

首次处理该项目，或需要核对截图与历史审计时，读 [项目背景与版本记录](references/project-context.md)。不要把里面固定日期的发现直接称为今天的最新状态。

## 从实际任务开始

1. 确认要交付的动作、车辆、阵营、起点、可用时间，以及代码和实车记录在哪里。先查仓库和知识库，只有影响判断的缺失信息才问用户。
2. 查看当前分支、完整提交编号和未提交改动；读取仓库约定。核对远端最新提交后，再判断用户说的“最新”是否也已安装到车上。需要检查其他版本时使用独立工作区，保留队员尚未提交的工作。
3. 比赛要求从知识库的官方来源进入，复核适用赛季、手册更新与赛事通知。规则、队内目标、假设和实测分开；不从动画截图推断完整规则。
4. 按需求只打开相关入口、Command、子系统、参数和测试。先说明已有能力、真正缺的连接、应在车上验证的条件；不因类名含 Auto 或存在一段发射代码就判定自动得分完成。

## 开发自动程序时

读 [自动程序开发与标定](references/autonomous-workflow.md)，重点遵守以下约定：

- 新自动入口放在 `opmodes/autos`，使用清楚的 Driver Station 显示名；参考现有路径结构，但重新核对坐标系、单位、起点朝向和目标。不要直接复制未验证的路线或另一台车的参数。
- 优先复用现有吸球、输送、发射子系统与 Command。先检查手柄依赖、调度器 requirements、启动与完成条件、超时及取消清理；有手柄依赖时，提取或适配可独立调用的动作，保留手动行为。
- Pedro 与手动 Drive 同时控制同一组底盘电机时会冲突。先明确每个阶段谁控制底盘，交接时停止上一控制者。
- 按“行驶到位 → 对准有效目标 → 达到发射条件 → 送球 → 确认结果 → 下一段”拆解。需要边走边吸时，明确路径结束后吸球何时结束；每个等待有截止和失败处理，整条路线有时间预算。
- 射击自适应只覆盖已实现的距离、转速和俯仰控制，不能代替命中、有效翻转、目标切换、球量与时间验证。若目标随翻转改变，设计翻转确认和下一目标选择。
- 标定参数来自当前车辆测量。网页或 Dashboard 改值后，要写回源文件、提交、重新构建安装并验证；编译成功不等于标定通过。

用户只要求分析时，给出依据和可执行步骤；要求修改时，完成授权范围内实现及相关检查。Skill 本身不授权安装到机器人、启动电机、向他人发消息、发布仓库或改变权限。

## 测试、合并和知识库交接

读 [协作与交付](references/collaboration-delivery.md)，并以仓库现行约定为准。

- 测试按影响范围选择。普通文字修改检查链接与事实；动作修改检查正常、边界、取消与恢复、DS STOP 及相关回归，保留具体版本和逐次结果。
- 区分“已写代码、构建通过、离线检查通过、实车通过、整场可用”。未取得实车记录写“待现场确认”，不据此判断队员没有测过。
- 一项任务一条分支。按当前环境命名约定建分支；本环境默认 `codex/` 前缀。普通改动至少 1 位非作者检查；核心动作、参数和接口代码由 2 位非作者检查，其中至少一位了解实车。AI 自检不能冒充队友批准。
- 代码 PR 对应确定版本的测试记录；合并后的最终代码版本重建并验证受影响动作。若只是整理 Skill 或知识库，不擅自修改机器人程序。
- 知识库沿用现有目录：任务与分工、参数、测试、日报、版本和交接分别写入对应位置；任务状态以 `plan/BOARD.md` 为准。没有姓名、结果或批准就不代填。
- 本知识库目前公开。仅记录必要的开发信息，不加入密码、账号密钥、个人评价或未经同意的学生影像。没有授权时只准备本地改动，不自动发布。

## 向同学和老师说明结果

使用高一同学容易理解的表达：先说“这一步车要做什么、现在卡在哪里、下一步怎么确认”，再解释相关代码；英文术语首次出现时补一句中文。不要用提交量或测试断言数量代替实际进度。

交付时说清：改了什么；对应哪个版本；已通过哪些检查；哪些仍需上车；队友从哪个文件或设备菜单继续。复用原任务卡和测试记录，不另造一套状态表。时间紧时按先后依赖收敛目标，保留用户明确提出的得分目标，并如实说明达到目标的前提。先了解队员经验；若只有少量上车时间且同学经验不足，复杂控制整合应由熟悉原程序的人提前准备或现场协助，同学分工操作、观察、计时和记录，不把数小时调试计划建立在新手现场完成多项复杂开发的假设上。
